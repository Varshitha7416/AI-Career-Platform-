# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

Two independent npm projects (no root package.json); run `npm install` in each:

- `server/` — Express 5 + Mongoose 9 API (CommonJS), port 5000
- `client/` — React 19 + Vite + Tailwind v4 SPA (ESM)
- `docs/` — numbered build-log notes (decisions and lessons per step); add a new numbered doc when finishing a major step

## Commands

Server (from `server/`):
- `npm run dev` (nodemon) / `npm start` — API on `PORT` (default 5000)
- `npm run seed` — seeds 12 Companies + 48 Jobs. **Deletes all existing Companies and Jobs.** Safety guard (runs before connecting): only a local MongoDB (`localhost`/`127.0.0.1`) is allowed; a remote/Atlas URI is refused unless `SEED_ALLOW_REMOTE_DB=<exact db name>` is set *and* `--force` is passed; `NODE_ENV=production` is always refused; a non-empty DB also needs `--force`. A URI with no database name means MongoDB's default db `test`
- `npm run seed:demo-jobs` — **additive** demo dataset: 26 companies and ~192 jobs (the original 48 jobs are kept and enriched in place with missing fields only; 144 new sample listings are added, keyed by `externalId` so reruns are no-ops). Never deletes or overwrites existing values, so saved jobs / applications / history stay valid. Dry run by default; `-- --apply` backs up `jobs`/`companies`/`counters` to `server/backups/` (verified, never overwritten) before writing and then creates the Job indexes. Same guard as the other scripts (local only; remote needs `SEED_ALLOW_REMOTE_DB=<exact db name>`; refuses `NODE_ENV=production`). Generated listings are flagged `source: 'demo'`; apply links are placeholders on `example.com`, never invented employer URLs
- `npm run seed:programs` — inserts the ~12 curated DEMO career programs (`source: 'demo'`, real provider names, provider home-page URLs only) by `slug`; never overwrites or deletes. Dry run by default, `-- --apply` to write; same guard as the other seed scripts (local only; remote needs `SEED_ALLOW_REMOTE_DB=<exact db name>`; refuses `NODE_ENV=production`)
- `npm run maintenance:orphan-saved-jobs` — finds SavedJob records whose Job was deleted. **Dry run by default** (reports saved-job orphans, and application orphans report-only; writes nothing). `-- --apply` deletes orphaned *saved jobs only*: it first writes a new timestamped, verified JSON backup to `server/backups/` (git-ignored; Extended JSON, restorable with `insertMany`), then re-checks each record is still orphaned right before deleting. Applications are never modified. Same guard principle as the seed script: refuses `NODE_ENV=production`, and refuses any non-local database unless `MAINTENANCE_ALLOW_REMOTE_DB=<exact db name>` is set (even for the dry run). Never runs automatically
- `npm run indexes` — controlled index management (dry run by default; `-- --apply` creates only missing, duplicate-free indexes and verifies them; never drops or alters). Index auto-creation at app startup is ON only for a local MongoDB and OFF for Atlas/remote (`AUTO_INDEX=true|false` overrides); see `docs/17-index-management.md`. Remote targets need `MAINTENANCE_ALLOW_REMOTE_DB=<db>` (a URI without a db name means `test`) and `--confirm-backup` to apply
- `npm test` runs the mocked unit tests (no database or network); the database-backed suites are the `test:*` scripts below and in `README.md` (each needs a throwaway local MongoDB)

Client (from `client/`): `npm run dev` (port 5173) / `npm run build` / `npm run lint`

Env: `server/.env` needs `MONGO_URI`, `JWT_SECRET` (server exits without them), `GEMINI_API_KEY` (AI endpoints return 503 without it). Optional: `PORT`, `GEMINI_MODEL`, `CLIENT_ORIGIN` (CORS allow-list, comma separated, default `http://localhost:5173`). Admin access is NOT env-driven (the old `ADMIN_EMAIL` auto-promotion was removed): create the first admin with `npm run bootstrap:admin` (see Email verification and first-admin bootstrap). See `server/.env.example`. Client: optional `VITE_API_URL` (default `http://localhost:5000/api`; see `client/.env.example`).

To test against a throwaway DB, override env at launch, e.g. `MONGO_URI=mongodb://127.0.0.1:27018/careernest_test PORT=5001 node server.js`, and `VITE_API_URL=http://localhost:5001/api npx vite`.

## Architecture

- **Server structure**: `server.js` mounts `routes/*Routes.js` under `/api/<resource>`; each route delegates to `controllers/*Controller.js`, which use `models/*.js`. Unknown routes hit `middleware/errorHandler.js` `notFound`; thrown/`next(err)` errors are normalised there (multer limits -> 413/400, Mongoose validation/cast -> 400, duplicate key -> 409, `err.status` honoured, else 500 `{message:'Server error'}`).
- **Auth**: `middleware/auth.js` `protect` verifies `Authorization: Bearer <jwt>` (401 with `code` `NO_TOKEN|INVALID_TOKEN|TOKEN_EXPIRED`) and sets `req.user = {id, role}`; `requireAdmin` gates job create/update/delete. Controllers **never trust a userId from the client**: they use `req.user.id`. Routes that still carry `:userId` (`GET /saved-jobs/:userId`, `GET /applications/:userId`) return 403 if it differs from the token user. Ownership is enforced by filtering queries on `user: req.user.id` (404 when not found). `middleware/validate.js` has `isValidId`, `isEmail`, `escapeRegex` (always escape user input used in `$regex`) and `validateIdParam`.
- **AI**: `config/gemini.js` `generateText(prompt)` is the single Gemini entry point (lazy client, model from `GEMINI_MODEL` default `gemini-3.6-flash`; maps failures to 502/503 with friendly messages). Model names get deprecated often — see `docs/02-ai-api-setup.md`. Analysis responses are fenced-JSON-stripped, parsed defensively, and the match % is clamped (null for general analysis).
- **Resume flow**: `POST /api/resumes` (multipart `resumeFile`; multer memory storage, 5MB limit, PDF only, `%PDF` magic-byte check) extracts text with `pdf-parse` v2 and stores `resumeText`. Responses never include `resumeText`. Cover letters/analyses use stored text + a populated `Job`.
- **Client**: `App.jsx` wraps pages in `ProtectedRoute` (checks `localStorage.token` and `user`) + `Layout`. Session lives in `localStorage` (`token`, `user`, `resumeId`) via `utils/auth.js`. `api/axiosClient.js` attaches the Bearer token and, on any 401 outside login/signup, clears the session and redirects to `/login?expired=1`. Shared UI in `components/Feedback.jsx` (skeletons, error/success/empty, `StatusBadge`); shared logic in `hooks/useJobActions.js` (save/unsave/apply state) and `hooks/useAllJobs.js` (pages through `/jobs` for dropdowns); `utils/errors.js` `getErrorMessage`. The `react-hooks/set-state-in-effect` lint rule is disabled inline on fetch-on-mount effects.

## Product

AI Career Platform for job seekers: job discovery (search/filter/save), application tracking, AI resume analysis (general or against a job), AI cover letter generation, and a referral marketplace (find employees at a company who will refer you). Stack: MongoDB Atlas + Mongoose, Express 5, React 19, Tailwind v4 (theme tokens `primary`, `primary-dark`, `accent`, `bg`, `charcoal` in `client/src/index.css`), Gemini for AI. The `docs/` files are step-by-step build journals (data modelling → AI setup → Express/Mongo → auth → jobs → saved jobs/applications → AI features/referrals → frontend). `docs/07` largely duplicates `docs/06`; `docs/01` describes an early data model that has since changed (e.g. Resume stores `resumeText`, not `fileUrl`).

## Data model (`server/models/`)

All schemas use `timestamps: true`; relations are ObjectId refs, populated in controllers.

- `User`: name, email (unique), bcrypt `password`, `role` (default `jobseeker`), `seekingRole`, `isReferrer`, `currentCompany`, `currentCompanyRole`, optional recommendation preferences (`preferredLocation`, `preferredWorkMode`, `preferredEmploymentType`, `experienceYears`)
- `Company`: name (unique), industry, location, description, website, logoUrl (optional; UI falls back to an initials tile), size. `server.js` requires it explicitly so `populate('company')` always has the model registered.
- `Job`: original fields (title, `company` ref **Company**, city, jobDescription, `experienceLevel` fresher|experienced, `yearsRequired`, `postedBy`) plus additive, optional fields: `jobCode` (CN-000123, from the atomic `Counter` model), `source` (`demo|manual|api`), `externalId` (future live-data feed), `isActive`, `postedAt`, `country`, `employmentType` (full-time|part-time|contract|internship), `workMode` (onsite|hybrid|remote), `experienceMinYears/MaxYears`, `salaryMin/Max/Currency/Period` + derived `salaryMaxInr` (fixed demo FX rates in `utils/salary.js`, for comparing/sorting only), `skills`, `preferredSkills`, `responsibilities`, `requirements`, `education`, `applyUrl` (http(s) only). A `pre('validate')` hook derives experience/salary fields and assigns `jobCode`; admin updates use load+save so these stay in sync
- `Resume`: user, fileName, `resumeText` (extracted text only; raw files are never stored)
- `ResumeAnalysis`: user, resume, optional job, matchPercentage, missingSkills[], strengths[], suggestions[]
- `CoverLetter`: user, job, resume, generatedText
- `SavedJob`: user + job. `Application` (status enum `applied|interviewing|rejected|offer`): user + job + `appliedAt` + `applyMethod` (`external` = user confirmed applying via the employer link, `manual` = user recorded an application made elsewhere). Duplicates are prevented by a `findOne` check plus a unique (user, job) index on both
- `Referral`: seeker, referrer (both User), message, status enum `requested|accepted|declined|referred`
- Dashboard-era models: `Interview` (user, application, job, scheduledAt, durationMinutes, mode video/phone/onsite, type screening/technical/hr/managerial/final/other, location, notes, status scheduled/completed/cancelled), `Notification` (user, type application/interview/referral/system, title, message, link, read), `Program` (slug, title, provider, description, category, level, duration, skills, url, theme, `source: 'demo'`), `ProgramEnrollment` (user, program, status saved/in-progress/completed; unique per user+program), `ContactMessage`. `Application.statusHistory` records status changes (older records derive a synthetic history, no migration); `User.notificationPrefs` {applications, interviews, referrals} defaults all true.

## Jobs feature notes

- **Recommendations are rule-based, not AI.** `GET /jobs/recommended` scores active jobs (excluding ones the user applied to) on: target role (`User.seekingRole`) vs job title (up to 40), skills from the user's latest resume matched against job skills (up to 40), experience fit (10), preferred city (10), work mode (5), employment type (5). Each result carries `matchScore` and human-readable `matchReasons`. With no usable profile signal it returns the latest jobs with `personalized: false` and says so; the UI labels the two cases "Matched to your profile" vs "Latest jobs".
- **Apply workflow** (`client/src/components/ApplyFlow.jsx`): with an `applyUrl` it opens the employer page in a new tab and then asks "Did you complete your application?"; the application is recorded (`applyMethod: external`) only when the user confirms. Without a link it states that plainly and offers an explicit "I applied elsewhere" manual entry (`applyMethod: manual`, with a date). Clicking Apply alone never writes anything. The Dashboard's saved-job button links to the job page instead of applying.
- **Demo data**: all generated listings are `source: 'demo'` and the UI shows a "Demo" badge and a disclaimer; they are not verified live vacancies. `externalId` + `source: 'api'` are the hooks for a future live-data integration.

## Dashboard feature notes

- **Shell** (`components/Layout.jsx` wraps every protected route): `TopBar` (Home, About, Profile, theme toggle, notification bell, Contact Us, avatar menu, page title that is NOT an h1) + `Sidebar` + `main`. The sidebar is collapsed to only the compact CareerNest brand tile; hovering or clicking it expands the dark forest-green panel as an overlay (click pins/unpins, leaving collapses unless pinned, Esc/outside click close, mobile = drawer). Items: Dashboard, Find Jobs, Saved Jobs, Applications, Interviews, Career Programs, Resume AI, Cover Letter, Referrals, Profile, Settings (`components/navConfig.js`). There is deliberately no "Upgrade to Pro". Visible naming: the job-search page is "Job Discovery" everywhere except the sidebar item, which the spec names "Find Jobs"; API routes and DB names are unchanged.
- **Theme**: `ThemeProvider` + `useTheme()` (`hooks/useTheme.js`; `theme` light/dark/system, persisted in `localStorage['careernest-theme']`, applied to `<html data-theme>` before first paint by a script in `index.html`; default is light). Dark mode works by remapping the semantic tokens in `src/index.css` plus a few unlayered overrides, and Tailwind's `dark:` variant follows `[data-theme=dark]`. Pages must use only semantic tokens (bg-white, text-ink, text-primary, border-sage/..., bg-mint) so both themes work; fixed palette colours are used only for status pills and the dark-green progress card.
- **Dashboard page** (`pages/Dashboard.jsx` + `components/dashboard/**`) renders `useDashboard()` (`hooks/useDashboard.js`: one overview request, range changes refetch `?range=` and keep the previous data visible). SVG donut chart and progress ring are hand built (no chart dependency). Everything is real data with honest empty states; no fabricated interviews or activity.
- **Notifications**: the bell polls `/notifications` every 60s and on focus; other pages can refresh it with `window.dispatchEvent(new Event('careernest:notifications-changed'))`.
- **Interviews** are real records created from an application (Application details or the Interviews page); the dashboard's upcoming list and the "attend an interview" milestone read them.

## Skill Gap Analysis feature notes

Full contract in `docs/21-skill-gap-contract.md`. ## Password reset and email (docs/22)

`POST /api/auth/forgot-password` and `POST /api/auth/reset-password` (public). Emails go through `server/services/email` (`sendEmail(template, to, data)`, transport interface, templates separate). **Development uses a local outbox**: emails are stored in MongoDB (`OutboxEmail`), never sent. The outbox transport and its model exist **only when `NODE_ENV` is exactly `development` or `test`** (unset/`Production`/`prod` => no outbox, forgot-password answers 503, and `EMAIL_TRANSPORT=outbox` or `DEV_OUTBOX_ENABLED=true` stop the server from starting). The viewer is opt-in (`DEV_OUTBOX_ENABLED=true`), GET-only, loopback Host+port, no proxy headers, and needs the per-process key printed at start-up (`X-Dev-Outbox-Key`). No real provider is configured yet (Phase 5). **Coordination**: one `AuthRecoveryState` document per account holds the cooldown, hourly budget, DB-assigned `seq` and the single usable link; issue = reserve -> create -> send -> activate (compare-and-set on `seq`), consume = one atomic update, and there is **no un-consume path** (a failure after consume answers `503 RESET_INTERRUPTED`). `AuthToken` is only the audit record (hash only). No per-email 429 (anti-lockout); per-account limits are DB-backed and silent. A profile password change revokes reset links. The emailed link carries the token in the URL fragment; `client/index.html` extracts it before the bundle. Env: `EMAIL_TRANSPORT`, `EMAIL_FROM`, `APP_BASE_URL`, `RESET_TOKEN_TTL_MINUTES`, `RESET_COOLDOWN_SECONDS`, `RESET_MAX_PER_HOUR`, `DEV_OUTBOX_ENABLED`, `AUTH_FORGOT_IP_MAX`, `AUTH_FORGOT_WINDOW_MINUTES`, `AUTH_RESET_MAX` (see `server/.env.example`). Tests: `npm test` (includes `tests/email`), `npm run test:reset` (`RESET_TEST_MONGO`; real multi-process + fault injection via `AUTH_TEST_FAULT`, `NODE_ENV=test` only) and `npm test` in `client/`. Design, race analysis and review findings: `docs/22`.

## Email verification and first-admin bootstrap (docs/23)

`User.emailVerified/emailVerifiedAt`; signup emails a link (`/verify-email#token=...`, same fragment handling as reset; AuthToken purpose `email_verification`, 24h, single use, SHA-256 only, purpose-isolated from `password_reset`). Endpoints: `POST /auth/verify-email` (public), `POST /auth/verification/resend` (token), `POST /auth/verification/request` (public, non-enumerating). Unverified users can log in and browse; `middleware/requireVerified.js` (`requireVerified('doing x')` -> 403 `EMAIL_NOT_VERIFIED`) gates applications, interviews create/update, referral requests/actions, AI generation (resume analysis, cover letters, skill gap, roadmaps) and contact. Policy table in docs/23. Client: `/verify-email` page and `VerifyEmailBanner` in `Layout`. First admin: `npm run bootstrap:admin -- --email <verified account>` with `BOOTSTRAP_ADMIN_SECRET` (24+ chars, typed again at a hidden prompt or `BOOTSTRAP_ADMIN_SECRET_INPUT` + `--yes`); refuses if any admin exists, atomic sentinel (`adminbootstrap` collection) so concurrent runs yield one admin, local DB only unless `BOOTSTRAP_ALLOW_REMOTE_DB=<db>`, production needs `BOOTSTRAP_ALLOW_PRODUCTION=true`. Tests: `npm test` (unit) and `npm run test:verify` (`VERIFY_TEST_MONGO`).

## Dual AI provider (docs/32)

`config/gemini.js` is now a facade over `services/ai/manager.js`: Gemini stays primary (its transport/retry/JSON logic moved unchanged to `services/ai/providers/geminiProvider.js`); Groq (`providers/groqProvider.js`, plain fetch, free tier only, `GROQ_MODEL` default `openai/gpt-oss-120b`, provisional) is a one-attempt fallback for quota/rate-limit/5xx/timeout/network/bad-JSON, never for bad requests or bad input. Per-provider circuit breakers (`breaker.js`) skip a failing provider and probe it again after the cooldown. The fallback is OFF unless `GROQ_API_KEY` is set AND `GROQ_PRIVACY_ACK=true` (privacy gate). One user request is still one `consumeAiCall`: fallback happens inside the single `generateJSON` call. `GET /api/admin/ai/health` (admin only, passive, no keys). No `XAI_API_KEY`: xAI Grok is not used. Tests: `npm test` (mocked only; no live AI calls).

## Optional email verification (docs/31, supersedes the gating policy in docs/23)

Verification is OPTIONAL. No route uses `requireVerified` any more (applications, interviews, referrals, AI tools, contact all work for unverified users); the middleware file is kept for a future action that truly needs a proven address. Verification itself (signup email, `/verify-email`, resend, banner, Settings status) still works and is never auto-granted. The one place verification still matters is the first-admin bootstrap, which requires a verified account. Password reset needs no flag: the emailed link itself proves inbox ownership.

## Known gaps / gotchas

- Unique (user, job) indexes on SavedJob/Application are built on startup; a DB that already holds duplicate pairs will log an index error until they are removed.
- Automated tests: mocked unit tests (`npm test`) plus database-backed suites run against a throwaway local MongoDB. The client has a small `node --test` suite. End-to-end browser flows are verified manually.
- Referral status transitions are not constrained beyond the allowed set (referrer can move accepted <-> declined).
- Admins manage jobs, companies, programs and support tickets in the admin UI (`/admin/...`); a first admin is created with `npm run bootstrap:admin`.
- No real email provider is configured yet: password reset and verification emails cannot be delivered outside development (docs/22).
- Career program content is curated demo data (provider home-page links only), not a live course catalogue. Interview scheduling is manual; there is no calendar sync or reminders by email.
- The Dashboard was built from the written spec because the reference image was not received; a visual-fidelity pass against that image is still open.
- `seed.js` **deletes all Companies and Jobs**; see the guard described under Commands. Saved/applied entries pointing at removed jobs are hidden by the API.
- The uploaded `.env` (gitignored) holds real credentials — never print or commit it.

## Batch 2: Settings (docs/27)

`User.notificationPrefs` has six booleans (`applications, interviews, referrals, programs, reminders, support`; default true, only an explicit `false` disables). `utils/notify.js` exports the single type->category mapping (`PREF_KEY`: application/interview/referral/program/reminder/support; `system` always delivered) and refuses tombstoned users: call `notify(userId, {type, title, message, link})` and prefs are enforced for you. `PUT /auth/profile` accepts booleans for known keys only (unknown keys 400). Settings page: Account (email + verification status), Security (`components/account/SecuritySection.jsx`: change password, resend verification), Your data and privacy. The account-deletion sweep also re-scans recent tombstones for stray rows; partial index `deleted_sweep_idx` on User. Tests: `SETTINGS_TEST_MONGO=... npm run test:settings`.
