## New data model (additive, no destructive migration)
**User** (new optional fields; keep every existing field): `phone` (string ≤20, digits/+ - () spaces), `location` (≤100), `headline` (≤120), `bio` (≤600), `linkedinUrl`/`githubUrl`/`portfolioUrl` (http(s) only, ≤300), `experienceLevel` ('fresher'|'experienced'), `education:[{institution, degree, fieldOfStudy, startYear, endYear, grade}]` (max 10), `experiences:[{company, title, startDate, endDate, current, description}]` (max 10), `skills:[{name, level?}]` (max 40; `level` optional enum `beginner|intermediate|advanced|expert` set only by the user, never defaulted), `domains:[string]` (max 10), `careerInterests:[{role, roleKey}]` (**max 3**, unique by lower-cased trimmed `roleKey`, role ≤80), `primaryRole` (string, must equal one of the interest roles). `seekingRole` stays and is kept in sync with the primary role (so the dashboard, recommendations and referrals keep working). **Backward compatibility without a migration:** API output derives `careerInterests` from `seekingRole` when the stored list is empty (one interest, primary); the stored list is written on the next profile save. A small role taxonomy (`server/utils/roles.js`, ~40 common roles with aliases) powers a searchable selector (`GET /auth/roles?q=`), custom roles are allowed.
**Resume** (new optional fields): `targetRole` (string|null), `targetRoleKey` (lower-cased trimmed, indexed with user). Rules enforced on the SERVER: a resume can only target one of the user's CURRENT career interests; at most ONE resume per interest role (assigning/uploading a new resume for a role that already has one un-assigns the old one: it stays in the library, nothing is deleted) and at most 3 role-assigned resumes; resumes without a role (all legacy ones, and ones uploaded elsewhere) stay valid and are "unassigned"; removing an interest un-assigns its resume (never deletes it); the default resume is the fallback. **Minimum-one rule:** the last remaining resume of a user cannot be deleted (409 `LAST_RESUME`, friendly message: upload another first); "resume-ready" = at least one resume. Unassigned library resumes stay unlimited (existing Resume Analyzer / Cover Letter flows unchanged).

## API contract
- `GET /auth/me` and `PUT /auth/profile` return/accept the extended user (`publicUser`): all new fields plus `createdAt` (member since), `careerInterests` (derived as above), `primaryRole`, and in `/auth/me` only: `resumeSummary:{count, roleResumeCount, resumeReady, unassignedCount}` (login payload unchanged). `PUT /auth/profile` stays partial-update, per-field validation with `errors:{field}` map (same style as signup), career interests validation (dup → 400 `DUPLICATE_ROLE`, >3 → 400 `TOO_MANY_ROLES`), primary role must be one of them (default: the first), password-change rules unchanged (returns new `token`). Never trust client ids; mass assignment blocked (`role`, `tokenVersion`, `_id`, email).
- `GET /auth/roles?q=` → `{roles:[string]}` (taxonomy search, max 15).
- `GET /resumes` DTO adds `targetRole` (string|null) and `roleAssigned` (bool); `POST /resumes` (multipart) accepts optional `targetRole`; `PUT /resumes/:id` accepts `{name?, isDefault?, targetRole?: string|null}` (null/'' un-assigns); errors `ROLE_NOT_IN_INTERESTS`, `TOO_MANY_ROLE_RESUMES`; response may include `replaced:{_id,name}` when an older resume was un-assigned; `DELETE /resumes/:id` → 409 `LAST_RESUME` when it is the only one. Existing response shapes stay compatible; existing upload validation (PDF/DOCX/TXT, 5 MB, magic bytes) unchanged.
- `GET /jobs/recommended?limit=` stays backward compatible (`{jobs, personalized, message, signals}`) and ADDS `groups:[{role, roleKey, isPrimary, resume:{_id,name,source:'role'|'default-fallback'|'none'}|null, basis:'role-resume'|'default-resume'|'profile-skills'|'role-only', jobs:[{...job, matchScore, matchReasons, matchedRole}]}]` — one group per career interest, scored with THAT role's resume (role-assigned resume), fallback = the default resume clearly marked `default-fallback`, else profile skills (`User.skills`) / role-title only (`basis` says which, `matchReasons` are human-readable and truthful); `jobs` stays the merged list (each job once, best group, `matchedRole`, `matchedResume`). Computed per request (no caching) so role/resume/profile changes apply immediately. No interests and no resume → latest jobs with `personalized:false` as today. Jobs UI: tabs "All recommended" + one per role, shows the matching role chip and which resume was used ("Role resume" / "Default resume (fallback)" / "Profile skills"), explains the basis, empty states for each case (3 roles/1 resume, resume without role, role without resume, none).
- Dashboard overview's profile completeness keeps its weights: `seekingRole` is satisfied by a non-empty `careerInterests`/primary role; `resume` by ≥1 resume (so Home/Dashboard numbers stay consistent).
